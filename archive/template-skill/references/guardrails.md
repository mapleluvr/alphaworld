
# Guardrails

本附件处理容易误用的边界，不代替主文件的工作链条。

## 1. 工作流程

用户指定 test-first 或 test-last 时，按该顺序执行。

通用最佳实践可以作为建议，不能自动升级为任务要求。
出现具体冲突时，说明冲突及影响；不要反复宣传另一种流程，
也不要以更换整个流程代替解决具体问题。

同样，不把“生成优先”解释为“必须先写生产代码”。
一个测试、接口草图或使用示例，也可能是在生成新的结构。

## 2. 风险与任务范围

根据错误的代价和可逆性安排验证。

原型中的低代价失败可以通过后续修改处理。
支付、权限、隐私、数据迁移和不可逆删除等环节，需要及时
建立相应保护，不能仅以降低调用次数为由省略。

增加检查应有明确依据：任务要求、已观察到的问题，
或足以影响交付的重要风险。

低频不等于不重要，边界情况也不自动值得穷尽。
避免无依据地扩大范围，也避免无依据地忽略风险。

## 3. 测试的用途

测试数量不是质量标准。每项测试应对应至少一种用途：

- 确认约定的行为；
- 澄清接口或设计；
- 保护重要的不变量；
- 防止已知问题再次发生。

临时探索测试可以在失去用途后调整或移除。
验收、契约和回归测试可能长期有用，不因代码稳定就失效。

优先保护外部行为和重要约束。依赖内部实现细节的测试，
需要确认其必要性，避免让无关重构造成大量失败。

测试通过不代表全部需求都已满足。
不能只实现测试中的几个样本而遗漏已约定的行为。

## 4. 失败后的修改

测试失败后，区分：

- 需求或理解有误；
- 测试表达有误；
- 实现有误；
- 环境或依赖有误。

不要默认实现一定错，也不要为了变绿而放宽断言、删除测试
或改写需求。修改测试同样需要需求或事实依据。

一次失败不自动意味着必须推翻整个方案。
先定位影响范围，再决定局部修改还是重新设计。

## 5. 工作粒度与费用

不要默认按函数、文件或固定行数分割执行。

每次拆分应有具体原因，例如关键依赖、上下文容量、
用户要求或高代价风险。明确部分应尽量连续完成。

TDD 的红—绿—重构循环，不天然对应独立的模型调用、
用户确认或长篇报告。具体开销取决于 Agent 的执行机制。

检查成本时，关注实际发生的重复读取、模型输入输出、
工具执行、规划和返工；不要仅凭测试次数推算费用。

预算限制应由可观测用量和运行器控制共同落实。
看不到实际计费数据时，可以减少明显浪费，但不能声称
已保证账单上限。

## 6. 暂停、完成与报告

局部成果不能被包装成完整交付。

执行或预算受限时，保存可续接状态，并说明：
已完成什么、哪些验证实际运行过、还缺什么。

预计无法在预算内完成时，及时提出范围、时间或预算的取舍，
不要无限继续，也不要静默降低交付标准。

完成后不自行追加重构、优化或测试范围。
必要但未执行的检查应明确标注，不虚报通过。

## 7. 表达与反思

只在影响决策时简要说明原因，不逐轮重复方法论。

用可观察行为描述问题，例如“无视 test-last 指令”
或“重复规划但没有推进”，不借模型的“创伤”“恐惧”
等心理推测解释其行为。

反思应产生有依据的调整；没有新问题时，不强行找错。
