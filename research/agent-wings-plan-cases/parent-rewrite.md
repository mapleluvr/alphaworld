# Agent Wings 基础设施推进计划 · Alphaworld 候选

本稿依据[原规划](agent-wings-infrastructure.md)、三个项目的首版规划和赛事草案改写。它重新组织后续工作的依赖与判断依据，不替代赛事规则，也不授予新的执行权限。文中仓库与调研现状沿用资料记载，本次没有重新验收远端、运行环境或服务能力。

## 要形成的交付

建立直播展示平台、sandboxing、Wings Ray 三个独立项目，使一条正式运行能够被可信地执行、计量、评判和展示。参赛进程在隔离环境中完成任务，通过受限通道调用指定模型；可信评测侧保留运行、费用和产物记录；展示平台只发布获准公开的事实，由 OBS Studio 录制和推流。

第一条真实运行用于帮助各项目形成可工作的连接方式。正式比赛还需要独立环境重置、跨队隔离、异常结算、容量测量和完整演练等证据。

沿用赛事的 Pi 0.87.1 基线、统一改进包和多目标评分。指定平台与模型要求覆盖主 Agent、子代理和工具背后的模型调用。评分权重、rollout 次数、预算与资源保障上限、晋级规则均以赛事公示为准，本计划不补写数值。准备阶段的测试支持额度也不作为正式评测预算。

## 现在先取得哪些能改变下一步的信息

以下准备按各自依赖推进。某项输入未到，只阻塞依赖它的工作。

### 从实际任务确定环境需求

从公开参考任务和校对材料中，选取能代表近期适配需求的一项，列出运行所需软件、文件格式、GUI/GPU、网络与状态重置条件。尚未拿到任务材料时，保留选择未定；仅凭 `Office` 等标签，无法确定是否必须使用原生 Windows 应用。

同时明确可用主机、系统与资源、虚拟化能力、已有服务所有权，以及允许新建和回收的专属资源。这些信息决定 Linux 候选能否承担任务、是否需要独立 Windows backend，也决定后续实验的授权范围。

WSL2 是 Linux workload 的优先验证候选。参考项目 kappa-box 的读取时 HEAD 为 `d1688eb386fd800b2c7d28d1ccd1a2ff34e04cf3`，runtime 有未提交修改；其 2026-09-12 历史摘要支持生命周期与 `exec(id)` 曾跑通，profile 仍为 `unverified`。host 组失败说明其验收门槛未通过，单凭该摘要不能判定 guest 已能逃逸。

因此，后续实验要取得比赛目标主机上的新证据。原生 Windows 要求进入独立 backend 验证；Linux 候选不能满足实际边界时，再沿具体失败原因比较独立虚拟机等路线。已有调查结论继续保留，不复用 kappa-box 的实例、端口、密钥或未验收能力声明。

### 找到可信记录的产生位置

在落实 runner/评分器归属时，一并确认谁登记 rollout 身份、输入与改进包版本，谁持有运行与终止权限，谁保留正式样本和原始证据。先通过 Pi 0.87.1 的实际源码或现有记录核对可用事件、RPC、日志和产物出口，后续再由真实运行验证。

这一步形成数据来源说明：什么能从源端取得，什么仍缺少，以及哪些字段允许公开。它供平台准备接入与展示，也供 Router 核对请求归属；暂不冻结 API 路径、JSON schema 或共享 SDK。

没有真实样本时，可在规划中明确待取样内容；已有的开发回放应标明来源和回放性质。源端能力未知的部分保持未知，不能由页面演示补成已实现状态。

### 等需求单决定 Wings Ray 的修改范围

Wings Ray 在需求单到达前保持 R0，不开展定制开发或部署。需求到达后，将每项行为落实为上游配置、接口适配或代码修改，并附上对应的验证路径。

赛事集成至少要回答：Pi 0.87.1 到指定模型的协议是否保留工具调用、流式响应及所需多模态语义；运行权限怎样限制、撤销并关联到正式 rollout；重试、取消和延迟结算怎样对账。这些问题约束赛事身份的使用，不自动成为 Router 全体用户的产品限制。

平台的数据来源梳理和 sandbox 的任务需求盘点，可以在需求单等待期间继续。实际模型调用与计量联调则等待需求、部署条件和授权到位。

### 将直播规格落实到实际使用条件

确认 OBS 主机与显示配置、是否与其他服务同机、目标直播服务、音视频规格、延迟需求、导播方式和可公开内容范围。

保留专用只读 Web 展示页加 OBS Browser Source 的首条路线，后台导播与公开画面分离。技术栈和接入方式由实际数据与部署条件决定。直播间尚未获授权时，只安排获准范围内的本地录制；本地录像不能证明推流接收端已经工作。

这些准备应留下可直接用于下一步的任务环境说明、数据来源、需求差异与授权事项。输入已经足够的部分沿用已有判断，不再重复整份选型论证。

## 获得授权后，用一条真实路径形成连接方式

先用主办方已审阅的参考包，在专属实验环境里完成一队、一题、一次 rollout。涉及不可信执行的安装和运行，先具备与该实验相应的保护；正式队伍准入另按完整隔离要求验收。

各项目可以先完成自身已经明确的准备与开发测试。连接真实路径时，需要落实 runner 归属、目标任务和环境、Router 需求与运行权限，以及 OBS 本地录制条件。某条依赖未满足时，保留已获得的其他证据；联合结果等待这条依赖补齐。

| 经过的环节 | 这一环节需要留下什么 | 据此确定什么 |
| --- | --- | --- |
| runner 登记并启动任务 | 可信的队伍、题目、rollout、输入、改进包和环境版本关系；正式起点。 | 运行身份与请求、产物如何关联，记录和控制由谁持有。 |
| sandbox 准备、执行和回收 | 本次实际策略、资源生效值、执行状态、材料进入及产物封存、终止与删除结果。 | 生命周期和文件通道的实际语义；仍缺哪些隔离证据。 |
| Wings Ray 转发与结算 | 受限身份调用指定模型的真实记录，包含子代理和工具调用归属，保留上游结果与结算状态。 | 请求与 rollout 的可信映射、撤销和异常对账方式。 |
| 评分侧读取产物与记录 | 实际被检查的产物版本、硬性检查、模型裁判及人工复核所需的证据范围。 | 产物封存与评判交接方式，暂定结果到最终成绩的区别。 |
| 平台接入并由 OBS 录制 | 服务端筛选后的公开事实、本地录像及与源记录的对应关系。 | 状态、费用、时间和成绩怎样显示，哪些信息需要延迟发布。 |

这里确定的是需要观察的关系，不预设字段名和协议形状。用真实样本写出调用与展示例子，先采用足以支撑这些关系的接口；通过运行和异常路径检验后，再固定各仓可依赖的契约及版本对应。

例如，若任务结束时费用尚未结算，就把执行结束与计量完成分别表达，展示端显示待结算及最后更新时间；若源端本就支持可靠重放，则沿用其语义，避免再发明一套事实源。已有接口满足需要时，直接接入。

异常也沿影响范围处理。发现重复事件先定位其发生位置与累计行为，修正接入或对账；发现任务需要原生 Windows，则调整相应环境路线。两类发现都不自动要求重写所有仓库的安排。

## 让这条路径具备正式使用的条件

首条路径跑通后，依据各仓规划补齐真实边界和失败路径，记录证据覆盖的主机、内核、引擎、策略、包/镜像、服务和 OBS 版本。发生相关变化时，重验受影响的部分。

sandbox 的准入依据是[验证矩阵](../../../agentwings-sandbox/docs/PLAN.md)：文件、网络、凭据、资源、生命周期、产物及应用兼容性均需要实际行为证据，包括跨队访问、越界链接、资源压力、孤儿进程和稳定快照。独立 rollout 按约定恢复状态，缓存规则对各队一致。Linux 与原生 Windows 的兼容性分别记录。

跨仓联调要验证：禁网任务仍可走受控 Router 数据面，管理面及上游密钥留在可信侧；失败、取消、重试及后续结算可归属；断线后正式运行的持有者、终止责任和恢复对账仍明确。正式样本完整保留，费用和成绩由权威记录及复核产生。

平台在可信服务端做白名单、脱敏和发布控制，原始证据、公开事件与最终成绩分别保存和授权。不可信网页、文档及其他产物经独立预览或渲染边界；OBS 不加载队伍任意页面，也不持有后台凭据。页面刷新、OBS 断开和导播切换只影响展示，不改变任务、预算或成绩；缺失与未结算数据明确显示，不记作零。

随后扩展到多队并列画面、评分板及授权直播间推流，验证实际接收端音视频与故障遮挡。并发、限额、录制规格和容量由需求、主机条件与实测确定，不从一次成功外推。

发布前固定跨仓版本与构建产物，完成容量实测、独立审阅和完整赛事演练，明确可用范围、回滚方法与故障责任。关键边界未知或失败的环境不进入正式可用列表；参考样本成功也不替代正式的多次 rollout 和复核。

Wings Ray 保留上游 AGPLv3、NOTICE、作者归属及可见上游链接要求。发布版本、对应源码提供和其他适用义务在部署前落实；具体维护方式沿用其[项目规划](../../../wings-ray/WINGS_RAY_PLAN.md)。

## 完成依据与续接

本轮规划工作的完成依据是：分仓与来源可检查，固定要求和候选判断可区分，近期每项工作知道缺什么、所得结果用于哪里，环境变更与付费操作留有明确授权入口。

后续实施的完成依据是整条运行链及正式准入证据。需要暂停时，保留已使用的版本、实际运行过的检查、受影响的缺口和下一步所需条件。用户输入或实测改变关键判断时，更新相关安排，其余有效成果继续使用。
